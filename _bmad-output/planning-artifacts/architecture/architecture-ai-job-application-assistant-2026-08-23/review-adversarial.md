# Adversarial Review — ARCHITECTURE-SPINE.md

Дата: 2026-08-23
Ревьюер: adversarial architecture review
Вердикт: **ADOPT WITH CHANGES** — каркас держит, но найдено 4 дыры, через которые два независимых билдера, каждый формально соблюдающий все AD, строят несовместимые системы.

Метод: сконструированы пары «юнитов» (клиентский модуль / серверный роут / LLM-слой), каждый из которых нарушает ни одного AD, но расходится со своим напарником в форме данных, владельце сущности или пути мутации состояния.

---

## F1 — Тон (FR-6): три несвязанных определения одной сущности

**Severity: HIGH**

**Сценарий.** Билдер A пишет в `shared/generate-contract.ts`:
`z.enum(["formal", "friendly", "enthusiastic"])`. Билдер B делает `ToneSelect`
с литеральными значениями `"official" | "casual" | "motivated"` и шлёт их в
`POST /api/generate`. Ни один AD не нарушен: AD-3 говорит лишь «тон — параметр
generate-запроса»; конвенция Shared types объявляет `shared/` источником типов,
но **не обязывает импортировать оттуда** — TypeScript молча компилирует
дубликат-литерал. Провайдерская `responseSchema` (AD-5 слой 2) — третье,
отдельное определение формы ответа, которое может разойтись с Zod-схемой
(слой 3): repair-retry тогда ловит рассинхрон как «невалидный вывод LLM»,
хотя сломан собственный контракт.

**Проверка существующих AD:** не закрывает. Конвенция декларативная, без
запрета на локальные дубликаты типов.

**Fix (tightened convention + AD-5):**
- Любая форма запроса/ответа API определяется **только** в `shared/*.ts`;
  литеральные дубликаты полей wire-формата в `client/` или `server/` запрещены —
  только импорт типа/схемы.
- Провайдерский `responseSchema` генерируется из Zod-схемы (`zod-to-json-schema`)
  либо проверяется тестом эквивалентности — ручное второе определение запрещено.
  То же для системного промпта: примеры JSON в промпте должны цитироваться
  из той же схемы, а не переписываться вручную.

## F2 — Сущность «вакансия»: два владельца лимита и две формы валидации

**Severity: HIGH**

**Сценарий.** AD-6 требует «вакансия ≤10 000 символов» на клиенте;
`POST /api/validate-vacancy` тоже валидирует. Билдер A считает лимит
`text.length` (UTF-16 units), билдер B — `Intl.Segmenter`/code points:
текст с эмодзи проходит у одного и падает `VACANCY_INVALID` у другого.
Хуже: конвенция Shared types покрывает только «Zod-схемы контракта **generate**» —
форму запроса/ответа `/api/validate-vacancy` никто не фиксирует. Билдер A
возвращает `{valid: true}`, билдер B — `{ok: true, data: {valid, charCount}}`,
третий — массив issues. Все трое соблюдают AD-7 (форма ошибки едина), но
успешные формы ответа валидации расходятся — клиент, написанный против одного,
ломается о другой.

**Fix (new sub-rule in AD-6 + tightened convention):**
- Конвенция переформулируется: «Zod-схемы **обоих** эндпоинтов
  (`validate-vacancy`, `generate`) и конверта `{ok, data|error}` — единственный
  источник типов клиента и сервера в `shared/`; конверт сам описан Zod-схемой».
- Лимит вакансии определён точно: **кодпоинты** (`[...text].length`), порог
  живёт в `shared/constants.ts` (один файл, импортируют обе стороны), а не в
  клиентском `constants.ts` и не в серверных константах по отдельности.

## F3 — Коды ошибок: закрытый список без процедуры расширения и без клиентских кодов

**Severity: MEDIUM**

**Сценарий.** AD-7 фиксирует 6 серверных кодов. Парсинг — целиком клиентский
(AD-4), и его ошибки не входят в список. Билдер A изобретает `PARSE_FAILED`,
билдер B — `PDF_CORRUPTED`, UI-компонент StageTracker маппит по строкам
первого. Формально AD-7 не нарушен (он говорит про серверные эндпоинты), но
единая форма `{code, message}` де-факто протекает и в клиентские фейлы, где
реестра нет. Плюс нет правила, что делать с кодом, отсутствующим в списке:
клиент, увидев незнакомый код (новый лимит добавили на сервере), падает или
показывает raw message.

**Fix (tightened AD-7):**
- Реестр кодов дополняется клиентскими (`PARSE_FAILED`) и помечается:
  список **закрытый**; новый код допустим только правкой таблицы конвенций
  в спайне (одна строка диффа).
- Правило отображения: неизвестный код → generic fallback UI-сообщение
  (`UNKNOWN_ERROR`), никогда stack trace / raw payload.

## F4 — PROMPTS.md: ручное копирование гарантированно протухнет

**Severity: LOW–MEDIUM**

**Сценарий.** AD-5: «промпты версионируются текстом в репозитории и
**копируются** в PROMPTS.md при изменении». Два билдера меняют промпт в
`server/src/prompts/` независимо; копирование забывают оба раза из двух.
PROMPTS.md — заявленный артефакт проверки anti-fabrication — теперь лжёт.
Никакой AD это не ловит: правило существует, но не enforceable.

**Fix (tightened AD-5):**
- PROMPTS.md — генерируемый экспорт (`npm run sync-prompts` собирает его из
  `server/src/prompts/`), а не ручная копия; CI/check: diff пуст.
  Либо честно понизить статус PROMPTS.md до «нормативен `src/prompts/`,
  MD — снимок на дату», убрав слово «копируются при изменении» как
  неисполнимое обязательство.

## Отклонённые атаки (существующие AD закрывают)

- **Обход BFF напрямую к Gemini** — закрыто AD-2 жёстко (единственный путь).
- **Server-side state / job ids** — закрыто AD-3.
- **Расхождение таймаутов клиент/сервер (90 c race)** — приемлемо: retry по
  кнопке = новый POST (AD-6), гонка деградирует в лишний 4xx/abort, не в
  некорректность данных.
- **Двойная мутация стадии пайплайна** (flows/ vs компоненты) — риск низкий:
  запрет глобального стора + React-поток данных делают конфликт маловероятным;
  отдельный AD на MVP не оправдан. Возвращаться к этому, если появится второй
  сценарий (UJ-2+).

## Итог

Спайн жизнеспособен для 2-day MVP после четырёх точечных правок: F1/F2 —
усилить конвенцию shared-types до обязательного импорта и распространить на
оба эндпоинта + конверт; F3 — закрытый реестр кодов включая клиентские;
F4 — генерация PROMPTS.md вместо ручной синхронизации. Ни одна правка не
добавляет кода сверх одной схемы/скрипта.
