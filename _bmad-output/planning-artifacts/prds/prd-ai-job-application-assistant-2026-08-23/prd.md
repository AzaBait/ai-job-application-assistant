# PRD: AI Job Application Assistant

## 0. Назначение документа

PRD для MVP сервиса адаптации резюме под вакансию. Аудитория: владелец продукта (Aza) и downstream-воркфлоу — UX (`bmad-ux`), архитектура (`bmad-architecture`), эпики/сторис. Документ строится поверх финализированного Product Brief (`_bmad-output/planning-artifacts/briefs/brief-ai-job-application-assistant-2026-08-23/`) — концепция, рынок и обоснования там; здесь только требования. Фичи сгруппированы, FR пронумерованы глобально (FR-1…FR-N) для стабильных ссылок. Технические решения — в аддендум и архитектуру, не сюда.

## 1. Видение

Веб-сервис без регистрации: соискатель загружает резюме, вставляет вакансию, выбирает тональность — получает адаптированное резюме и сопроводительное письмо для скачивания в PDF/DOCX. Ключевой принцип — **ничего не выдумывать**: генерация опирается только на факты исходного резюме.

MVP реализуется в рамках двухдневного интенсива. Приоритет — один полностью рабочий end-to-end сценарий; всё, что ему не служит, — за границей PRD.

## 2. Целевой пользователь

### 2.1 Jobs To Be Done

- Когда я откликаюсь на очередную вакансию, я хочу быстро получить резюме, заточенное под её требования, — чтобы не править одно и то же руками.
- Когда мне нужно сопроводительное письмо, я хочу получить его из своего реального опыта — чтобы не писать с нуля и не выдумывать.
- Я хочу быть уверен, что сервис не добавит мне несуществующий опыт — чтобы не попасть в неловкую ситуацию у рекрутера.
- Я хочу просто зайти и получить результат — чтобы не регистрироваться и не оставлять свои данные.

### 2.2 Не-пользователи (v1)

- Рекрутеры и HR-отделы (это инструмент соискателя).
- Команды, которым нужен трекинг откликов и CRM (не наш продукт).

### 2.3 Ключевой пользовательский сценарий

- **UJ-1. Мария адаптирует резюме под конкретную вакансию.**
  - **Персона + контекст:** Мария, мидл-разработчик, откликается на несколько вакансий в неделю и устала вручную переписывать резюме под каждую.
  - **Вход:** открыла сайт, аккаунта нет и не нужен.
  - **Путь:** загружает своё резюме PDF → вставляет текст вакансии → выбирает тональность → запускает генерацию → видит прогресс по стадиям → получает два документа.
  - **Кульминация:** скачивает адаптированное резюме и письмо, каждое в PDF или DOCX, — и отправляет отклик.
  - **Развязка:** закрывает сайт; ничего о ней не сохраняется.
  - **Edge case:** файл повреждён или вставленный текст не похож на вакансию — Мария видит понятное сообщение и исправляет ввод, не начав всё заново.

## 3. Глоссарий

- **Резюме** — исходный документ пользователя, загруженный в формате PDF или DOCX. Единственный источник фактов для генерации.
- **Вакансия** — текст описания вакансии, вставленный пользователем. Источник требований и ключевых слов.
- **Тональность** — выбранный пользователем стиль формулировок результата.
- **Генерация** — процесс создания результата через AI API.
- **Адаптированное резюме** — результат Генерации: Резюме, переформулированное и реструктурированное под Вакансию, без новых фактов.
- **Сопроводительное письмо** — результат Генерации: письмо под конкретную Вакансию на основе фактов Резюме.
- **Результат** — пара документов: Адаптированное резюме + Сопроводительное письмо.

## 4. Фичи

### 4.1 Загрузка резюме

**Описание:** пользователь загружает Резюме в формате PDF или DOCX. Сервис извлекает текст до запуска Генерации; при проблеме предлагает загрузить другой файл. Реализует UJ-1.

#### FR-1: Загрузка файла резюме

Пользователь может загрузить Резюме в формате PDF или DOCX.

**Следствия (проверяемые):**
- Принимаются файлы форматов PDF и DOCX `[ASSUMPTION: лимит размера ~5 МБ]`.
- Файлы других форматов отклоняются до обработки с сообщением о поддерживаемых форматах.
- Из принятого файла извлекается текст; если извлечение невозможно (повреждённый файл, скан без текстового слоя), пользователь получает понятное сообщение об ошибке и возможность загрузить другой файл.

#### FR-2: Понятная ошибка при невалидном файле

При невалидном файле пользователь видит человекочитаемое сообщение (что не так и что делать), а не техническую диагностику.

**Следствия:**
- Сообщение называет причину: неподдерживаемый формат / повреждённый файл / текст не извлекается.
- После ошибки пользователь может загрузить другой файл без перезапуска сценария.

### 4.2 Ввод вакансии

**Описание:** пользователь вставляет текст Вакансии в текстовое поле. Сервис проверяет, что текст похож на описание вакансии и достаточен для адаптации; сомнительный ввод не проходит молча. Реализует UJ-1.

#### FR-3: Ввод текста вакансии

Пользователь может вставить произвольный текст Вакансии в текстовое поле.

**Следствия:**
- Поле принимает многострочный текст разумной длины `[ASSUMPTION: лимит ~10 000 символов]`.

#### FR-4: Валидация вакансии до генерации

Сервис проверяет введённый текст на соответствие ожиданиям от описания вакансии перед Генерацией.

**Следствия:**
- Если текст не является описанием вакансии или содержит недостаточно информации для адаптации, Генерация не запускается; пользователь видит понятное сообщение и просьбу предоставить корректное описание.
- Проверка выполняется без сохранения данных `[ASSUMPTION: проверка выполняется тем же LLM-вызовом или лёгкой эвристикой — решение за архитектурой]`.
- Ориентиры pass/fail: проходит — типичное описание с названием позиции, обязанностями и требованиями; не проходит — случайный текст («Lorem ipsum», рецепт блюда), обрывок в несколько слов без упоминания работы.

#### FR-5: Разноязычный ввод не блокируется

Сервис не требует совпадения языка Резюме и Вакансии как precondition и не блокирует сценарий по языковому признаку на уровне MVP.

**Следствия:**
- Отсутствует проверка «языки совпадают» как precondition.
- Точный языковой scope — открытый вопрос (§8).

### 4.3 Выбор тональности

**Описание:** пользователь выбирает Тональность из предложенного списка до Генерации; выбор влияет на оба документа Результата. Реализует UJ-1.

#### FR-6: Выбор тональности

Пользователь может выбрать одну Тональность из фиксированного набора.

**Следствия:**
- Набор содержит несколько различимых вариантов `[ASSUMPTION: 3–4 варианта, например «профессиональная», «дружелюбная», «уверенная»; точный список и названия решаются на этапе UX]`.
- Есть значение по умолчанию, чтобы сценарий работал без обязательного выбора `[ASSUMPTION]`.

### 4.4 Генерация без фабрикации

**Описание:** ядро сервиса. Сервис генерирует Адаптированное резюме и Сопроводительное письмо через AI API строго на основе фактов Резюме и требований Вакансии. Принцип достоверности — продуктовое ограничение первого порядка, а не пожелание. Реализует UJ-1.

#### FR-7: Генерация Адаптированного резюме

Сервис генерирует Адаптированное резюме: переформулирование, реструктуризация, выделение релевантного опыта и использование ключевых слов Вакансии.

**Следствия:**
- Результат не содержит фактов (опыт, навыки, образование, проекты, достижения), отсутствующих в Резюме.
- Формулировки могут изменяться; структура может меняться; факты — нет.

#### FR-8: Генерация Сопроводительного письма

Сервис генерирует Сопроводительное письмо под Вакансию на основе фактов Резюме и выбранной Тональности.

**Следствия:**
- Те же ограничения достоверности, что и во FR-7.
- Письмо учитывает выбранную Тональность.

**Feature-specific NFR:**
- Промпты спроектированы против фабрикации; ключевые промпты фиксируются в PROMPTS.md (обязательный артефакт интенсива).

### 4.5 Стадии процесса и обработка ошибок

**Описание:** во время обработки пользователь видит, что происходит и на какой стадии находится сервис. Ошибки — понятные сообщения, а не stack trace. Реализует UJ-1.

#### FR-9: Индикация стадий процесса

Пользователь видит состояние процесса на каждой стадии.

**Следствия:**
- Отображаются состояния: загрузка файла → анализ резюме → анализ вакансии → генерация результата → успешное завершение; отдельное состояние — ошибка генерации. Названия стадий — UX-лейблы для пользователя, а не обязательный пайплайн бэкенда `[NOTE FOR PM]`.
- Во время активных стадий интерфейс показывает прогресс/спиннер; повторный запуск заблокирован до завершения `[ASSUMPTION]`.

#### FR-10: Понятные сообщения об ошибках генерации

При недоступности AI API или ошибке Генерации пользователь получает понятное сообщение с возможностью повторить попытку.

**Следствия:**
- Никаких stack trace или технических деталей в UI.
- Сообщение объясняет, что произошла временная ошибка, и предлагает повторить `[ASSUMPTION: ретрай доступен одной кнопкой]`.

### 4.6 Экспорт результатов

**Описание:** пользователь скачивает каждый документ Результата отдельно в PDF или DOCX. Реализует UJ-1.

#### FR-11: Скачивание документов

Пользователь может скачать Адаптированное резюме и Сопроводительное письмо, каждое в формате PDF или DOCX.

**Следствия:**
- Оба формата доступны для обоих документов (всего 4 варианта скачивания).
- Структура документа (заголовки, списки, разделители) читаема в скачанном файле `[ASSUMPTION: идеальное форматирование не гарантируется — приемлемый уровень для MVP определяет UX/дев]`.

## 5. Non-Goals (явные)

- Никакой регистрации, авторизации, профилей.
- Никакого хранения пользовательских данных между сессиями — стейтлесс by design.
- Никакого diff-просмотра изменений резюме в v1.
- Никаких интеграций с job-платформами, автозаполнения заявок, парсинга ссылок на вакансии.
- Никакой монетизации в v1.
- Никакого трекинга откликов и истории генераций.

## 6. Границы MVP

### 6.1 Внутри

- Загрузка PDF/DOCX с валидацией (FR-1–2)
- Ввод и валидация вакансии (FR-3–5)
- Выбор тональности (FR-6)
- Генерация обоих документов без фабрикации (FR-7–8)
- Стадии процесса и понятные ошибки (FR-9–10)
- Экспорт PDF/DOCX (FR-11)
- Качественный адаптивный UI (критерии качества — зона `bmad-ux`)
- Deploy · README.md · PROMPTS.md

**Сквозное ограничение безопасности:** API-ключи AI-провайдера не хранятся и не используются на клиенте. Механизм (серверный прокси или эквивалент) — решение архитектуры, но само ограничение нерушимо для MVP.

### 6.2 Вне MVP

Всё из §5 Non-Goals. Обоснование одно: не служит end-to-end сценарию двухдневного MVP.

## 7. Метрики успеха

Ставки учебного интенсива — метрики демонстрационные, не продуктовая аналитика.

**Основные**
- **SM-1**: End-to-end прохождение — пользователь от загрузки до скачивания обоих документов проходит сценарий успешно за минуты на финальной презентации. Валидирует FR-1–FR-11.
- **SM-2**: Достоверность — в Результатах демо-сессий отсутствуют факты, которых нет в исходном резюме (ручная проверка). Валидирует FR-7, FR-8.

**Вторичные**
- **SM-3**: Устойчивость — заведомо некорректные входы (битый файл, текст-не-вакансия, недоступный API) получают понятные сообщения, а не падение. Валидирует FR-2, FR-4, FR-10.
- **SM-4**: Демонстрируемость AI-процесса — финальная презентация показывает работу с AI, включая ошибки/галлюцинации модели и их исправление (обязательное требование интенсива). Валидирует FR-7–FR-10 в демонстрационном контексте.

**Контр-метрики (не оптимизировать)**
- **SM-C1**: Скорость генерации — не жертвуем достоверностью (SM-2) ради скорости ответа LLM.

## 8. Открытые вопросы

1. Языки интерфейса и генерируемых документов (перенесён из брифа; решение на этапе UX/требований к контенту).
2. Провайдер LLM и конкретный AI API (решение на этапе архитектуры: доступность API, качество, стоимость).
3. Точный языковой scope обработки разноязычных пар «резюме+вакансия».

- FR-3: лимит длины текста вакансии ~10 000 символов. **Подтверждено.**
- FR-4: механизм валидации вакансии (LLM vs эвристика) — за архитектурой.
